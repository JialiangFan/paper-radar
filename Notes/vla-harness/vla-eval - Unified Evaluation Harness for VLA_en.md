# vla-eval: A Unified Evaluation Harness for Vision-Language-Action Models

> arXiv: 2603.13966 | Year: 2026

## Topic
Unified VLA evaluation harness

## Background
Vision-Language-Action (VLA) models are increasingly evaluated on multiple simulation benchmarks to demonstrate cross-environment and cross-embodiment generalization, yet adding even one benchmark to an evaluation pipeline demands substantial engineering effort. Each benchmark ships its own simulator, Python runtime, and asset requirements (LIBERO needs Python 3.8 with robosuite, ManiSkill2 needs Python 3.10 with SAPIEN, CALVIN needs Python 3.8 with PyBullet), and no single environment satisfies all constraints simultaneously. Beyond dependency resolution, evaluation protocols are frequently underspecified — seeds, episode counts, and preprocessing details are omitted from papers. Following the decoupled design of `lm-evaluation-harness` for language models, this work fully separates model inference from benchmark execution.

## Limitations & Research Problem
- **Limitation:** Evaluating N models on M benchmarks means repeating the integration process M times independently for each model — an O(N × M) burden that makes comprehensive multi-benchmark evaluation impractical for small teams. Underspecified protocols compound this: correct integration requires painstaking comparison against reference implementations, since a single undocumented parameter can shift success rates by up to 55 percentage points.
- **Problem:** Can a unified harness let models integrate once and benchmarks integrate once, so that the full N × M cross-evaluation matrix works automatically (reducing integration effort from O(N × M) to O(N + M)), while preserving reproduction fidelity to reference implementations and drastically cutting wall-clock evaluation time?

## Contributions
- An open-source evaluation harness supporting **14 simulation benchmarks** and **six model servers** with Docker-based isolation and a WebSocket+msgpack protocol; models integrate via a single `predict()` method, benchmarks via a four-method interface.
- Validation across **six VLA codebases and three benchmarks**, reproducing published scores and documenting previously **undocumented pitfalls** where one parameter shifts success rates by up to 55 pp.
- A model-agnostic parallel evaluation methodology (episode sharding + batch inference) achieving up to **47× wall-clock speedup** (2,000 LIBERO episodes: ~14 h → ~18 min); the bottleneck is environment step rate, not model inference.
- A VLA leaderboard with canonical protocol definitions, aggregating **657 published results across 17 benchmarks**.

## Methodology
- **Architecture:** A client-server split over WebSocket with msgpack binary serialization. Each message carries a type (observation, action, episode_start/end), a benchmark-specific payload, a sequence number, and a timestamp.
- **Model servers:** Extend `PredictModelServer`, which exposes a blocking `predict(obs, ctx)` (typically ~50 lines), with automatic action chunking and optional batched inference via `max_batch_size`.
- **Dependency isolation:** Model servers declare dependencies via PEP 723 inline metadata; `vla-eval serve` launches each through `uv run`, creating an isolated environment automatically. Conflicting dependencies (CogACT pinning `transformers==4.40.1` vs. X-VLA requiring `transformers>=4.44`) coexist without interference, mirroring the Docker isolation used on the benchmark side.
- **Benchmark integration:** Integrators implement four methods — `reset`, `step`, `make_obs`, `get_step_result` — inside a dedicated Docker image with pinned dependencies.
- **Declarative configs:** Two YAML configs (benchmark + model server) drive each evaluation. All Docker images are published to ghcr.io with versioned tags and bundle every required asset (scene files, textures, robot descriptions), eliminating ad-hoc asset installation. A complete evaluation requires only two commands: `vla-eval serve` and `vla-eval run`. Every run emits a structured JSON result file recording the harness version, benchmark configuration, and per-episode metrics.
- **Parallelism:** Environment parallelism uses episode sharding across K Docker containers; inference parallelism uses batched forward passes. Parallelism is tuned by a demand/supply methodology — λ(K) measures environment throughput as a function of shards, μ(B) measures model throughput as a function of batch size, and the operating point satisfies λ(K) < 0.8·μ(B*) to prevent queue buildup.
- **Leaderboard curation:** Canonical protocol definitions were established per benchmark (standardizing task subsets, metrics, splits, and comparability constraints), since SimplerEnv spans three incomparable robot configurations, CALVIN ABC→D and ABCD→D splits are not comparable, and LIBERO papers report either 4 or 5 suites. An AI agent (Claude Code with Opus 4.6) then reviewed 1,704 papers via MCP tool integrations (arXiv, Semantic Scholar, PDF reader) to extract and normalize results against those protocols; a human operator reviewed every entry, resolving anomalies and ambiguous cases. Each entry is versioned with full provenance metadata and validated against automated schema constraints.

## Experiments & Key Numbers
- **Scope:** Table I lists 14 benchmarks with action spaces from 6D to 14D and compressed Docker images from 4.7 GB (RLBench) to 35.6 GB (RoboCasa). Three are marked cross-codebase reproduction verified (SimplerEnv, LIBERO, CALVIN); the other eleven are integrated but not yet cross-validated. The six model servers are CogACT, OpenVLA, OpenVLA-OFT, π0/π0-FAST, GR00T N1, and X-VLA.
- **Parallel speedup (LIBERO + CogACT-7B, H100 model server, separate benchmark host):** Episode sharding from K=1 to K=50 increases environment throughput by **32.6×** (λ: 11.2 → 364.6 obs/s); batch inference from B=1 to B=16 increases model server throughput by **2.8×** (μ: 165.2 → 468.2 obs/s). Combined, 2,000 episodes complete in ~18 minutes versus ~14 hours sequentially — a **47× wall-clock speedup**. The operating point K*=50 uses 78% of the supply capacity at B=16; beyond K=80, environment overhead causes throughput to drop.
- **Other benchmarks:** CALVIN — 1,000 sequences, 16 shards, ~33 min, **16×** (from 8.6 h). SimplerEnv — 288 episodes (3 seeds), 16 shards, ~8.5 min, **12×** (from 1.7 h).
- **Reproduction matrix (Table II, ours with Δ vs. reported):** Protocols are LIBERO 4 suites × 10 tasks × 50 episodes (2,000 total), CALVIN ABC→D with 1,000 chained sequences, and SimplerEnv with 4 WidowX tasks × 24 episodes. LIBERO (%): OpenVLA 76.2 (−0.3), π0.5 97.7 (+0.8), OpenVLA-OFT 96.7 (−0.4), GR00T N1.6 94.9 (−2.1, community checkpoint), DB-CogACT 94.7 (−0.2), X-VLA 97.4 (−0.7). CALVIN (len): DB-CogACT 4.02 (−0.04), X-VLA 4.30 (−0.13). SimplerEnv (%): GR00T N1.6 59.7 (−8.0, Google Robot visual matching), DB-CogACT 63.5 (−6.0), X-VLA 94.8 (−1.0).
- **Undocumented pitfalls:**
  1. **X-VLA / proprioceptive state source:** Using the wrong source on LIBERO drops success rate from 97.8% to 42% — a **55 pp** swing from one parameter.
  2. **Absolute vs. delta action modes:** Both are valid 7D vectors and indistinguishable from data alone; confusing them yields **0%** success as positions accumulate and the robot diverges.
  3. **OpenVLA-OFT / quaternion-to-axis-angle:** The reference conversion omits antipodal normalization (angle ∈ [0, 2π], matching the robosuite convention), while the authors' initial implementation flipped w < 0 quaternions (angle ∈ [0, π]); this single mismatch dropped LIBERO-Goal from 97% to 83% and LIBERO-Long from 95% to 56%.
  4. **OpenVLA / evaluation-time center crop:** A center crop (scale = 0.9) applied at evaluation is not documented in the paper; omitting it costs ~**3 pp**.
  5. **GR00T / end-effector pose input:** GR00T expects end-effector pose as proprioceptive input, but this field exists only in an internal simulator fork, not in official SimplerEnv; without it, scores drop from 30–55% to **0%**. Reimplementing the necessary patches brought GR00T on SimplerEnv (Google Robot) from 0% to 59.7%, with a −8.0 pp gap to the reported score remaining.
  - Each of these was discovered only through systematic comparison of intermediate values against reference implementations.
- **Leaderboard and cross-benchmark analysis:** Aggregates **657 results across 17 benchmarks and 509+ configurations**, sourced from **1,704 papers** citing at least one tracked benchmark. Coverage distribution over 509+ models (Fig. 5): **81% (410) are evaluated on a single benchmark**, 13% (66) on two, 5% (24) on three, 2% (9) on four or more, and only 3 models (0.6%) on five or more; only 6% cover three or more benchmarks. Cross-benchmark comparison is therefore rare.
- **Limitations:** The audit covers six codebases across three simulation benchmarks; additional benchmarks and real-robot transfer are planned. Leaderboard results are extracted from published papers, not independently verified. Supported metrics are limited to task success rate; finer-grained dimensions such as subtask progress, task efficiency, and safety are not yet supported.
