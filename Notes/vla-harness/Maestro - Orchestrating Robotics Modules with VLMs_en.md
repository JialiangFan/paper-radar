# MAESTRO: Orchestrating Robotics Modules with Vision-Language Models for Zero-Shot Generalist Robots

> arXiv: 2511.00917 | Year: 2025

## Topic
VLM-orchestrated modular zero-shot manipulation

## Background
The prevailing route toward generalist robots is to collect ever-larger "observations-in actions-out" teleoperation datasets and train end-to-end vision-language-action (VLA) models, replicating the recipe that worked for VLMs. This paper takes the opposite road: rather than training a new policy, it builds a generalist policy directly around an off-the-shelf VLM by augmenting it with a carefully curated set of perception, planning, and control modules, which a VLM coding agent dynamically composes into a programmatic policy for the current task and scenario. The approach belongs to the code-as-policies (CaP) lineage, but the authors argue the bottleneck of prior CaP systems is not the VLM itself — it is a narrow tool repertoire and manually imposed structural constraints.

## Limitations & Research Problem
- **Limitation:** End-to-end VLAs depend on costly large-scale real-robot teleoperation data; their training distribution is dominated by pick-and-place, yielding near-zero progress on out-of-distribution tasks such as opening a cabinet or rotating a cube, and they lack any explicit memory mechanism. They also forfeit the interpretability, debuggability, and extensibility that modular systems provide natively.
- **Limitation:** Prior CaP work is either open-loop (a static program that cannot respond to unexpected events during execution) or restricted to a limited tool set covering pick-and-place of simple, symmetric objects. Even the closed-loop Gemini Robotics CaP system is reported to be significantly inferior to its own teleoperation-trained VLA counterpart. More broadly, in these pipelines large models automate only a small portion of the stack while the rest remains hand-engineered rigid workflow, which limits scaling to diverse in-the-wild scenarios.
- **Problem:** Without using any robotics training data, can scaling the *breadth and quality of the toolset* while *stripping away manually imposed workflow structure* let a VLM agent zero-shot match or surpass state-of-the-art VLAs on challenging manipulation skills, and transfer cheaply to new embodiments?

## Contributions
- MAESTRO (Managerial Agent for Executing Sensorimotor Tasks in RObotics): a VLM-driven agentic framework that writes and executes code to orchestrate five module families — perception, geometry, control, learned visuomotor policies, and image editing — inside a closed-loop plan–react–replan perception–action–learning cycle, spanning tabletop and mobile embodiments.
- Zero-shot evaluation on 7 tabletop and 4 mobile manipulation tasks, outperforming π0, π0.5, and a Gemini Robotics Agent CaP baseline on 6 of 7 tabletop tasks.
- Systematic ablations isolating which design choices matter most (advanced perception and geometry modules), and analysis of where the gains over prior CaP and VLA methods come from.
- An evolution mechanism that improves generated code from a small number of real-world trials, plus a hybrid usage pattern in which a VLA (π0.5) is itself incorporated as a callable module inside the tool repertoire.

## Methodology
- **Toolset design principles (Sec. III-A):** (1) A "coarse-to-fine" perception hierarchy — raw sensory input (fastest) → mask centroid → VLM-selected task-relevant keypoints (most precise; ReKep-inspired, overlaying a uniform point grid on a Grounded-SAM mask and asking GPT-o3 to pick the salient points) — giving the agent agency to trade execution speed against task performance; depth is estimated from RGB with FoundationStereo. (2) Active perception as an enabler that improves every other module (zoom in / look around for better point clouds and keypoints). (3) Geometry and linear-algebra modules (distance measurement, vector construction, relative rotation between vectors, rotating a vector by an angle) scaffold spatial reasoning, compensating for the lack of reliable spatial chain-of-thought in current VLMs. (4) A fast-inference VLM monitor — a locally hosted Qwen2.5-VL-72B-Instruct emitting yes/no task-completion checks at 2 Hz — to interrupt VLAs, which run fast but are not trained to stop themselves. (5) cuRobo point-cloud-based collision-free motion planning. (6) A cached semantic map of observed object locations for long-horizon mobile planning.
- **Closed-loop plan, react, replan (Sec. III-B):** Given an instruction and initial image, MAESTRO *plans* (decomposes into substeps, generates code for the first); after execution it *reacts* (ingests the original instruction, code output, robot state, and last-substep images to judge whether the subgoal was achieved); on success it plans the next substep, on failure it *replans* (diagnoses the likely cause and rewrites improved code for the same substep). In mobile settings it is additionally prompted to actively look around before failure analysis.
- **Evolution (Sec. III-C):** A database logs all past executions — generated code, stdout, and Gemini's success/failure analysis of the execution video. This accumulated record is supplied to Gemini as in-context examples before each run, so it refines code generation from prior successes and failures.
- **Module inventory:** Control exposes simple Cartesian primitives (move gripper to, open/close gripper); learned policies include the GraspGen grasp model and the π0.5 VLA; image editing offers draw points and overlay 6D poses to strengthen visual grounding; mobile-specific additions are Faster-LIO 6D state estimation, Nav2 navigation, a fine-grained "nudge" tool for local adjustment, look left/right/ground, view carry-on basket, remember object location, and put in basket.

## Experiments & Key Numbers
- **Setup:** Gemini Robotics-ER 1.5 as the VLM. The tabletop platform follows DROID (7-DoF Franka Emika Panda with a Robotiq 2F gripper, wrist-mounted plus third-person cameras); the mobile platform is a Unitree Go2-W wheeled quadruped with a top-mounted AgileX Robotics PiPER manipulator and a calibrated wrist camera. 7 tabletop and 4 mobile tasks. Evaluation follows the STAR-Gen generalization taxonomy, perturbing along four axes (visual changes to task-relevant objects, object poses, action verbs requiring new behavior, entirely new manipulated objects), giving 5 trials per task (1 initial setup + 4 STAR-Gen generated), held fixed across all compared methods. The metric is a 0–100 task-progress score decomposed into a sequence of verifiable sub-steps.
- **Baselines:** Gemini Robotics Agent (the Gemini Robotics technical-report CaP approach reimplemented with Gemini Robotics-ER 1.5), π0 (π0-FAST-DROID checkpoint), and π0.5 (π0.5-DROID checkpoint).
- **Tabletop (Table II; Gemini Robotics Agent / π0 / π0.5 / MAESTRO):** Put item in bowl 73.3±46.2 / 74.0±37.1 / 70.0±41.1 / **98.0±4.5**; Fold four corners of the towel into the center 40.0±17.3 / 47.0±25.1 / 70.0±15.4 / **71.3±21.4**; Open cabinet 3.3±5.8 / 8.3±2.9 / 0.0±0.0 / **68.0±31.3**; Rotate cube purple side up 23.6±3.5 / 29.0±1.7 / 10.0±0.0 / **60.0±38.1**; Cut banana with knife 71.0±28.8 / 30.0±23.9 / 14.0±6.5 / **92.0±5.7**; Hang mug on mug holder 46.0±23.2 / 59.0±30.7 / **80.0±14.1** / 69.0±9.6 (the single task where MAESTRO trails); Erase instructions on whiteboard, then stack cups 26.7±24.7 / 12.0±12.0 / 22.0±22.8 / **63.0±16.8**.
- **Mobile (Table III; MAESTRO only):** Collect all toys on table 85.0±22.4; Throw green ball into garbage can 76.7±14.9; Search item and put on table 96.0±8.9; Press button to open door 93.3±14.9. The two long-horizon tasks score lower due to multi-stage object interactions; the throwing-trash score of 76.7 is limited by occasionally inaccurate depth estimates of the garbage can, producing grasp poses that violate IK constraints and abort motions, and by the reactive replanning mechanism entering oscillatory loops when no collision-free path is found.
- **Ablation (Table IV; Fold Towel / Rotate Cube):** MAESTRO 71.3±21.4 / 60.0±38.1; MAESTRO w/o advanced perception 40.0±7.1 / 25.0±0.0; MAESTRO w/o geometry modules 67.5±3.5 / 42.5±31.8. Fold towel depends on precise interaction at the towel's corners, which the no-advanced-perception variant fails to identify; rotate cube depends on constructing vectors from task-relevant keypoints, so neither ablated variant makes progress.
- **Evolution:** Starting from the least successful open-cabinet run (35% progress: it identified the handle but attempted a top-down grasp that failed), one evolutionary update made it scan around the handle and use the grasp model to grasp successfully, though it still pulled straight rather than along the rotation axis, reaching 70.0±5.0; by the third evolution it used vectors constructed from handle and hinge keypoints to compute and apply the correct rotation, reaching 85.0±7.4.
- **Stated limitations:** Failures persist when complex chain-of-thought reasoning about object affordances and spatial orientation is required (e.g., hang mug — it fails to align the mug handle's hole with the branch orientation of the holder); MAESTRO also incurs higher latency and computational overhead than end-to-end VLA policies, with VLM API response times introducing pauses during react and replan. The authors frame runtime as a transitional limitation expected to close with VLM inference optimization, model distillation, and more efficient code generation.
