# Advanced Knowledge Base Debugging for Rulelog

## Research Problem
How to provide systematic debugging tools for large-scale Rulelog knowledge bases, including automatic non-termination diagnosis and justification-based explanation.

## Topic
Rulelog Knowledge Base Debugging Tools

## Background
Rulelog is an expressively rich knowledge representation and reasoning (KRR) logic, formulated as an extended form of declarative logic programs (LP) under the well-founded semantics. It uniquely combines higher-order syntax (HiLog), defeasibility based on argumentation theories (AT-defeasibility), rule cancellation and priorities, default and explicit negation, omniformity (classical-logic formula syntax), and bounded rationality (restraint). Rulelog has been implemented most fully in Silk (a Java layer atop Flora-2/XSB) and partially in Cyc, with strong interoperability with major semantic web standards including RDF(S), SPARQL, OWL-RL, RIF-Core, and RIF-BLD. The debugging approach described in this paper is part of an integrated development environment (Silklipse, based on Eclipse) designed to support knowledge engineers who are competent in logic but may not be computer programmers. The work was conducted as part of Vulcan's Project Halo advanced research effort.

## Limitations & Research Problem
- **Limitation 1:** The complexity of Rulelog's transformational semantics (from Rulelog to normal LP via tabled SLG resolution), combined with higher-order features and defeasibility, renders traditional Prolog-style interactive debuggers impractical for understanding Rulelog derivations.
- **Limitation 2:** Knowledge engineers construct knowledge bases declaratively with little attention to procedural behavior, leading to knowledge bases whose queries may exhibit poor performance or non-termination, especially when logical functions (introduced explicitly or implicitly via omniformity) generate infinite terms.
- **Problem 1 (Justification Problem):** How to explain missing or unexpected query answers in a system where defeasibility, higher-order reasoning, and complex rule transformations may cause answers to differ from expectations? This requires explaining why-not (NAF-false literals), how prioritization operates, and which arguments were defeated.
- **Problem 2 (Performance/Termination Problem):** How to diagnose runaway computations, including non-termination caused by function symbols and excessively large recursive components, where determining termination is in general undecidable and cost-based subgoal reordering with recursion and logical functions remains understudied?

## Contributions
- A comprehensive, integrated suite of debugging tools for expressively rich Rulelog knowledge bases, incorporated into the Silk/Silklipse IDE, addressing correctness, performance, and termination.
- **Justification tool:** An on-demand justification mechanism using a small set of meta-rules (rather than transforming original rules), supporting explanation of defeasible reasoning including why-not, prioritization, and defeated arguments. Justification is presented as a navigable tree in the GUI with color-coded icons indicating goal/argument/fact/priority status, and supports automatic transformation into English text summaries.
- **Table dump tool:** Leverages tabled LP inferencing tables to report the most heavily called subgoals, the subgoals with the most answers, and the most frequently invoked rules, enabling identification of performance bottlenecks.
- **Forest logging and recursive component analysis:** Based on XSB's forest log mechanism that records SLG resolution tabling events at the byte-code level (with less than 20-30% performance overhead), supporting analysis of logs containing hundreds of millions of facts. Includes recursive component analysis with abstraction routines (mode abstraction and predicate abstraction) to coalesce similar atoms in components with 10^5+ subqueries.
- **Terminyzer:** An automatic non-termination analyzer that performs call-sequence analysis and answer-flow analysis on forest logs to identify the specific sequences of subgoals and rules causing non-termination. It provides heuristic suggestions for runtime subgoal reordering using delay quantifiers (e.g., `wish(ground(?X))`) to prevent runaway computation.
- **Restraint mechanism:** Leverages Rulelog's built-in bounded rationality feature to prevent non-termination at the semantic level while maintaining soundness. Includes radial restraint (bounding term size/depth), skipping restraint (conditionally skipping rule instances), unsafety and unreturn restraint (handling NAF-unsafe literals and failed external queries), and anytime restraint (progressively incrementing the radius until a time limit).
- **Overall debugging process:** A systematic macro-to-micro workflow where table dump and forest logs identify macroscopic bottlenecks, Terminyzer pinpoints specific non-termination causes, and justification tools combined with restraint handle microscopic correctness and termination issues.

## Methodology
- **Justification (Section 2):** Unlike prior approaches that transform original rules and inflate the knowledge base, Silk invokes a separate small set of meta-rules on demand when the user requests justification. The system supports defeasible reasoning explanation through argumentation theories, visually distinguishing goals ("G"), arguments ("A"), facts ("F"), and prioritization ("P") with color coding (green for true, red for false; bang "!" for undefeated, down-arrow for defeated). Justification can be automatically rendered as English text via rule-based transformation.
- **Trace-based analysis (Section 3):** (1) Table dump examines XSB's tabled inferencing tables to produce statistics on subgoal call frequency and answer counts. (2) Forest logging uses an internal XSB flag to log all tabling operations (table_call, answer_return, etc.) as Prolog-readable facts with sequence counters; logs are loaded, indexed, and analyzed within XSB. (3) Recursive component analysis provides overviews of computation structure (total calls, distinct tabled subgoals, number of recursive components) with abstraction routines for manageable presentation. (4) Terminyzer operates on forest logs to perform call-sequence analysis (detecting repeatedly called subgoal/rule sequences) and answer-flow analysis (tracking how answers propagate), and heuristically suggests delay quantifier rewrites for subgoal reordering.
- **Restraint (Section 4):** Limits the semantics of inferencing by upper-bounding a norm on subgoals (term size or depth) via a radius parameter; derivations exceeding the limit receive the undefined truth value. Variants include skipping restraint (user-specified conditions for skipping rule instances via meta-rules), unsafety restraint (NAF-unsafe literals treated as undefined), unreturn restraint (non-returning external queries treated as undefined), and anytime restraint (computing increasingly complete result sets within a time budget by progressively incrementing the radius).
- **Incremental truth maintenance:** Rapid edit-test-inspect loops are enabled by incremental tabling methods in XSB and Flora-2, allowing interactive knowledge revision without full recomputation.
- **Overall debugging workflow (Section 5):** When a query executes within acceptable time/space, the user examines answers via justification tools for correctness. When runaway computation occurs, the user first inspects the table dump for deeply nested function symbols (indicating non-termination) or large tables (indicating inefficiency), then employs Terminyzer for precise diagnosis or forest log analysis for large recursive components, and finally applies restraint to ensure termination.
